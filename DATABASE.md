# Database — schema, migrations, backups

## Schema ownership

**Alembic owns the schema.** `models.py` is the source of truth; migrations in
`alembic/versions/` are generated by diffing the live database against it.

The application no longer creates tables at import time. Before starting the
server (or after pulling changes), run:

```bash
alembic upgrade head
```

### Changing the schema
1. Edit `models.py`
2. `alembic revision --autogenerate -m "what changed"`
3. **Read the generated migration** — autogenerate is a draft, not an authority
4. `alembic upgrade head`
5. Commit the model change *and* the migration together

### Checking for drift
```bash
alembic check          # fails if models and database disagree
alembic current        # which revision the database is on
alembic history        # all revisions
```

> On the legacy SQLite dev database `alembic check` reports cosmetic noise
> (`TEXT` vs `String`) and missing foreign keys — the original tables were
> created by raw SQL that never declared FK constraints. A database created
> fresh from the baseline migration has them.

## Migrations

| Revision | Purpose |
|---|---|
| `93d372c238b8` | Baseline — all 7 tables with FK + unique constraints |
| `ad91f789bba6` | Money → `NUMERIC(14,2)`; drop the SQLite-only `created_at` trigger; backfill NULL timestamps; add 7 indexes |

### Why `ad91f789bba6` matters
Two latent production bugs were fixed here:

1. **Money was `REAL` (float).** Binary floating point cannot represent decimal
   currency exactly, and the error compounds when summed. Now `NUMERIC(14,2)`,
   and `ExtractedInvoice` parses amounts straight to `Decimal` from the string
   form so no float ever touches the value.
2. **`invoices.created_at` was set by a SQLite-only trigger.** That trigger
   would not exist on Postgres, leaving `created_at` NULL — and billing's
   `count_invoices_this_month()` filters on it, so **every tenant would have
   appeared to use 0 invoices and received unlimited free usage**. The
   timestamp is now generated by the application (`models.utc_timestamp`),
   which behaves identically on every dialect.

## Postgres

`DATABASE_URL` is the only switch:

```bash
# .env
DATABASE_URL=postgresql://user:password@host/dbname   # or postgresql+psycopg://
```

`db.py` normalizes a plain `postgresql://`/`postgres://` scheme to
`postgresql+psycopg://` automatically, so either form works — SQLAlchemy
otherwise defaults to the (uninstalled) `psycopg2` driver and fails to import.
Requires the `psycopg[binary]` driver (pinned in `requirements.txt`).

Then `alembic upgrade head` builds the full schema from scratch — including
the foreign keys the original SQLite database never had (see above).

**Migrated to production Postgres on 2026-08-21.** All 46 rows (7 orgs, 9
users, 16 invoices, 2 email accounts/messages/attachments, 8 processing logs)
copied across preserving primary keys, with sequences reset past the migrated
max ids. Verified row-by-row equal to the SQLite source; all 9 API endpoints
return 200; a fresh `/extract` upload round-trip works; `created_at` on new
rows is populated by the application (no trigger) and billing's monthly usage
count correctly reflects it.

**Bonus finding during migration:** one legacy row (`BluePeak Systems`,
`INV-2026-1009`) had `gst`/`total` stored as comma-formatted *text*
(`"90,842.30"`) from before the AI-output Decimal normalization existed.
SQLite's numeric coercion was silently reading only the leading digits before
the comma (`90`, not `90,842.30`) whenever it computed `SUM(total)` — so every
dashboard total was quietly wrong by that gap. The Postgres migration script
correctly refused to guess (`Decimal("90,842.30")` raises, so it inserted
`NULL` rather than perpetuate the mis-parse); the value was then recovered
using the same comma-stripping logic as `ai_service.ExtractedInvoice` and
written back. Postgres now reports the **true** total, `683,705.26`, instead
of SQLite's silently-truncated `592,952.96`.

## Backups

**Local SQLite (development)**
```bash
cp invoice.db "invoice.db.backup-$(date +%Y%m%d-%H%M%S)"
```

**Restore drill** — a backup you have never restored is not a backup:
```bash
cp invoice.db.backup-YYYYMMDD-HHMMSS /tmp/restore-test.db
sqlite3 /tmp/restore-test.db "PRAGMA integrity_check; SELECT COUNT(*) FROM invoices;"
```
Last verified: 2026-08-03 — `integrity_check: ok`, 16 invoices, 9 users restored.

**Production (managed Postgres)** — use the provider's automated backups with
point-in-time recovery, and **schedule a quarterly restore drill into a scratch
database**. Document the measured RTO/RPO once tested.

## Known follow-ups
- `invoice_date` / `created_at` / `due_date` are still `TEXT` (ISO strings).
  They sort and compare correctly, but converting to real `DATE`/`TIMESTAMP`
  columns would allow date arithmetic and better indexing. Deferred because it
  changes API response formats the frontend parses.
- No `ON DELETE` behaviour is defined on foreign keys; deleting an organization
  would orphan its rows.
